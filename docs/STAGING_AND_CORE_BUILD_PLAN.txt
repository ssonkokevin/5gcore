1. VERDICT IN ONE PAGE

   The repo is further along than a prototype and further from staging than
   it looks. The problem is not missing features. It is that several
   components are present, wired, and not doing what their names say:

     - the stack cannot start: 12 host-port collisions in one compose file;
     - the GMLC, which is the product you intend to sell, returns an
       MD5 hash of the phone number mapped onto San Francisco;
     - the custom UPF reads packets and discards them, and says so;
     - the GMLC config declares MAP and Diameter as enabled; neither
       exists in its code;
     - bootstrap.sh starts services by names that do not exist;
     - the tests directory is empty.

   None of this is hard to fix. Most of it is a day's work. What it means
   is that no test result produced today can be trusted, because a passing
   test may be exercising a mock.

   Order of work, and it is not negotiable:

     Week 1   Correct the P0 list in section 3. Nothing is tested until
              the stack starts and stops lying about itself.
     Week 2   Bring up staging topology in section 4 and run the transport
              and Diameter tests in section 5.
     Week 3-4 Prove one end-to-end path with a real decision at the end of
              it: a location request that reaches a real GMLC, a real
              HSS, and returns a real answer or a real error.
     Then     Build, per section 6, in the order given.

   The single sentence to remember: a core that answers wrongly is worse
   than a core that refuses to start, because the wrong answer is believed.

 3.3 P0-2 THE GMLC IS A MOCK

   gmlc_server.py:185 builds a location from md5(msisdn):

     hash_val = int(hashlib.md5(msisdn.encode()).hexdigest()[:8], 16)
     lat = 37.7749 + (hash_val % 1000) / 10000.0
     lon = -122.4194 + ...

   Every result is in California. The two "Diameter" routes at
   gmlc_server.py:102-108 are HTTP POST handlers that echo JSON; no SCTP
   socket is opened anywhere in the file. The SLh handler returns result
   code 2001 with a computed "location", which is not what SLh does: SLh
   returns routing information, not position.

   Why this is the worst item in the list: the GMLC is the product. A
   demonstration built on this file will pass, look correct on a map, and
   be worthless. Delete the simulation path and make the service refuse
   to answer when no real source is configured. A 501 is a better
   product behaviour than a wrong coordinate.

 3.4 P0-3 THE GMLC CONFIG LIES

   gmlc/config/gmlc.yaml:26-39 sets:

     map:      enabled: true, stp_host osmo-stp, sctp_role client
     diameter: enabled: true, port 3869

   Neither is implemented. Configuration that says "enabled" for something
   absent is worse than configuration that says no, because operations
   trusts it. Two rules:

     - every "enabled" flag must be asserted at startup: if true and the
       dependency is missing, exit non-zero with a named error;
     - the GMLC must never start with both LCS sources disabled.

 3.5 P0-4 THE CUSTOM UPF IS NOT A UPF

   upf_server.py:24-33 binds UDP 8805 and 2152 and logs:

     "%s received %s bytes from %s (stub, not forwarded)"

   It reads the vendor dpe.json, cpe.json and dpeMgr.json and prints
   them. There is no eBPF program, no XDP hook, no GTP-U forwarding, no
   PFCP state machine.

   Consequence for the build documents: every statement about
   far_map_size, qer_map_size and urr_map_size applies to the WTL/vendor
   binary on the D: drive, not to this file. Do not size maps in this
   repo.

   Fix: rename it to something honest (pfcp-sniffer), or delete it. The
   staging data plane must be Free5GC's UPF (gtp5g) or the vendor binary.

 3.6 P0-5 AUTH VECTORS FAIL OPEN

   udm_server.py:1379, when the crypto module is unavailable:

     rand = secrets.token_hex(16).upper()
     keys = derive_5g_keys_simple(...)
     autn = hashlib.sha256(...)

   These are not 5G AKA vectors. No UE can validate them. In test the
   handler returns 200 and the engineer concludes authentication works;
   on a real SIM it fails. Authentication must fail closed. Replace the
   fallback with HTTP 500 and a metric.

 3.7 P0-6 THE 5G NFs HAVE NO CONFIG

   config/ contains one file, oam.json. The free5gc services receive only
   environment variables (AMF_ADDR, NRF_ADDR, GUAMI_*, ...). The upstream
   free5gc images read YAML from /free5gc/config and do not consume those
   variables by default.

   VERIFY: run `docker exec core-amf ls /free5gc/config` and check that
   amfcfg.yaml exists and matches your PLMN. If it does not, the AMF is
   running the image's default 001/01 configuration and nothing you set
   in compose is in effect.

   Fix: mount one config directory per NF, version it in git, and add a
   startup check that prints the loaded PLMN and NRF address.

 3.8 P0-7 BOOTSTRAP IS BROKEN

   scripts/bootstrap.sh:32 runs `docker-compose up -d stp dra scp udm oam`.
   The services are named osmo-stp, open5gs-dra, scp, udm/custom-udm, oam.
   `stp` and `dra` do not exist; the script fails part-way and leaves a
   half-built stack. Also, DB_ROOT_PASSWORD defaults to 123456 at
   bootstrap.sh:26.

   Fix: derive service names from `docker compose config --services`, and
   refuse to run if .env still contains "change-me".

 3.9 P0-8 THERE ARE NO TESTS

   tests/ exists and is empty. A staging environment without tests only
   proves that processes start. Section 5 supplies the test list; the
   first twelve belong in tests/smoke as executable checks, not prose.

 3.10 P1 -- CORRECT BUT NOT BLOCKING A START

   - SUCI: only the null scheme works; Profiles A and B return None at
     udm_server.py:1613. Compute SUCI Profiles A/B per TS 33.501 Annex C,
     or de-conceal at the AUSF. Until then, a production SIM with a
     concealed SUCI cannot attach.
   - HSS has no SLh: no 16777291 and no RIR/RIA anywhere in
     nhss_server.py. This answers verification item V2 as a NO. The GMLC's
     SLh leg has no server; either add it to the UDM (two weeks) or state
     in the product that SLh is not supported.
   - DRA routes only Cx: dra_engine.py:193 hardcodes 16777216. Add SLg,
     SLh, S6a, S6d, S13, Gx, Rx and the command codes from section 5.2.
   - GMLC command codes are wrong: it uses 302 for "SLh LIR" and 303 for
     "SLg SLR" (gmlc_server.py:161, 175). 302 is Server-Assignment in Cx;
     SLh RIR is 8388622 and SLg PLR is 8388620.
   - GMLC timestamps use loop time, not wall clock (gmlc_server.py:134).
     That value is a float since boot; it cannot be used in a CDR.
   - Request IDs restart at zero on every restart (self._request_counter).
     Make them durable and globally unique before anything is billed.
   - Privacy check is a single global comparison
     (gmlc_server.py:116-123). There is no per-client class, no LCS client
     table, no override audit. This is the LCS privacy model; it is not
     optional under UCC regulation.

 3.11 P2 -- BEFORE A CUSTOMER SEES IT

   - Secrets: .env.example ships "change-me" everywhere, and .gitignore
     covers .env but not a stray copy. Generate secrets; never commit.
   - OAM has no role separation surfaced in the tree; check before
     exposing it beyond localhost.
   - No signalling KPIs. Add counters for Diameter result codes, MAP
     errors, SCTP associations, PFCP sessions and GTP-U drops. Without
     them pre-production acceptance is opinion, not measurement.

5. SIGNALLING TEST PLAN

 5.0 THE PRINCIPLE

   Test at the lowest layer that can fail, and never accept a higher
   layer's success as proof of a lower one. A successful location answer
   proves nothing if the Diameter leg was mocked. Order: transport,
   then protocol, then procedure, then service.

   Every test below has: setup, action, observable, pass criterion. If a
   test cannot name its observable, it is not a test.

 5.1 LAYER 0 -- TRANSPORT

     T0.1  SCTP listening
       action      ss -lnts ; ss -lnup
       observable  the expected socket and port per section 4.2
       pass        every published port present, no duplicates

     T0.2  SCTP association to a peer
       action      sctp_test -H <local> -P <lport> -h <peer> -p <pport>
       observable  INIT/INIT-ACK in tcpdump, state ESTABLISHED
       pass        association up within 5 s, survives a 60 s idle

     T0.3  M3UA ASP state
       action      read osmo-stp VTY or logs
       observable  ASP-UP then ASP-ACTIVE for each AS
       pass        all AS active; one link down does not drop the AS

     T0.4  Diameter peer
       action      start the app, watch CER/CEA
       observable  CER sent, CEA with Result-Code 2001
       pass        peer table shows I-OPEN; DWR/DWA every 30 s

     T0.5  MTU and fragmentation
       action      send a 4 KB Diameter message over SCTP
       observable  reassembly succeeds; no silent truncation
       pass        full payload received and parsed

6. THE CUSTOM CODE PLAN

 6.1 PRINCIPLES

   1  One writer per datum. The UDM writes subscriber state; nobody
      else. If two services write, you have two truths.
   2  Fail closed. No fallback that fabricates a security artefact.
   3  Every interface has a specification and a test. No test, no merge.
   4  Stateless where possible, durable where required. Sessions in
      Redis are acceptable; CDRs and balances are not.
   5  No mock in a build that is called staging. A mock is a profile
      named mock, and its outputs are marked.

 6.2 SHARED LIBRARY

   Build once, use everywhere, in a package `corelib`:

     corelib/config      load, validate, assert-at-startup
     corelib/log         structured JSON, request and session correlation
     corelib/metrics     prometheus counters and histograms
     corelib/diameter    peer state machine, dictionary, AVP validation
     corelib/sbi         HTTP/2 client and server, problem+json errors
     corelib/pfcp        header, IE encode/decode, session table
     corelib/db          pooled access, migrations, outbox
     corelib/idgen       durable, monotonic request and session ids

   The absence of this library is why the GMLC, DRA and UDM each have
   their own half-implementations. Adding it is the highest-leverage

7. THE DIAMETER FIREWALL AND SS7 SCREENING

 7.1 WHY IT IS A PRODUCT, NOT A CONFIG

   Diameter has no authentication between peers beyond a shared transport
   and a configured name. Anything that can reach port 3868 can send an
   S6a Insert-Subscriber-Data, a Cancel-Location, or an SLg Provide-
   Location. SS7 is weaker still. The firewall is what stands between the
   interconnect and your subscriber data.

   It belongs in the DRA position, in front of every peer, and it is the
   thing you can sell to another operator.

 7.2 MESSAGE SCREENING

   Allow-list, default deny, evaluated on the inbound request before any
   routing decision:

     - peer identity: Origin-Host and Origin-Realm must match a
       configured peer; unknown peers get 3002 and an alarm;
     - application and command pair must be in the allowed matrix for
       that peer (a roaming partner may send SLg only if you sell it);
     - for SLg, the target IMSI must match a home prefix; otherwise
       drop and log with the prefix;
     - for S6a, ULR from an MME that is not yours is dropped;
     - no inbound request may target an NF that is not published to that
       peer.

 7.3 AVP VALIDATION

     - mandatory AVPs present, in the right order of occurrence;
     - AVP length sane against the message length;
     - no duplicate AVPs where the specification forbids them;
     - enumerated values in range (a Requested-QoS with a bogus class
       must be rejected, not clamped);
     - string AVPs printable and within length limits;
     - grouped AVPs validated recursively, to a bounded depth.

   Malformed input gets a defined error, never a parser exception that
   kills the process. Fuzz this on purpose.

 7.4 TOPOLOGY HIDING

   Rewrite Origin-Host and Origin-Realm on egress to your signalling
   identity. Never rewrite Session-Id, Hop-by-Hop or End-to-End Id. A
   firewall that rewrites session identifiers breaks every answer path
   and is very hard to diagnose.

 7.5 RATE, OVERLOAD AND DOIC

     - per-peer request rate cap and a burst allowance;
     - per-application cap, so a Gy storm cannot starve S6a;
     - answer with 3004 (too busy) rather than dropping, so the peer
       backs off;
     - implement DOIC per RFC 7683: advertise OC-Supported-Features,
       honour OC-OLR and OC-Validity-Duration, and shed in the order
       your policy names;
     - shed location requests first. They are the least revenue-critical
       and the most privacy-sensitive.

 7.6 MALFORMED AND HOSTILE INPUT

     - oversized messages rejected before allocation;
     - AVP count and nesting bounded;
     - unknown application ids answered 3007 or dropped with a counter;
     - SCTP association storm limited per source;
     - every rejection increments a labelled counter and writes an audit
       record with the peer, the message and the rule.

 7.7 LOGGING AND RECORDING

   One audit record per rejected message: timestamp, peer, application,
   command, rule id, and a hash of the payload. One performance record
   per interval: requests, answers, errors by code, latency percentiles.
   These are what you show a regulator and a customer.

 7.8 CONFIGURATION SCHEMA

   A versioned file, reloaded without restart, with the same evaluation
   shape as the DRA so operators learn one model:

     rules:
       - id: slg-inbound-roaming
         match: { application_id: 16777255 }
         when:  { imsi_prefix_not: ["256724"] }
         action: drop
         log: audit
       - id: s6a-from-home-mme
         match: { application_id: 16777251, command: 316 }
         when:  { origin_host_in: ["mme01", "mme02"] }
         action: route
         peer_set: hss

   First match wins. Rule ids are stable and appear in the audit record.

 7.9 ACCEPTANCE TESTS

     TFW.1  unknown peer                    dropped, 3002, alarm
     TFW.2  disallowed command              dropped, counted
     TFW.3  SLg from a foreign prefix       dropped, audit record
     TFW.4  malformed AVP                   defined error, process alive
     TFW.5  fuzz 10,000 random messages     no crash, no leak
     TFW.6  rate above cap                 3004, peer backs off
     TFW.7  OLR received                    shedding applied, restored
     TFW.8  reload rules under load         no message loss
     TFW.9  unknown GT at the STP           MAP error, not forwarded
     TFW.10 disallowed opcode at the STP    rejected, counted


8. KUBERNETES AND SERVER SETUP

 8.1 THE SCTP FACT FIRST

   Kubernetes Services support SCTP, but that is not the hard part. The
   hard part is that N2 (NGAP), N3 (GTP-U), Diameter and M3UA need a pod
   to have a stable, routable IP on a specific VLAN, and to own an SCTP
   association end to end.

   Practical rule:

     - signalling NFs (amf, dra, stp, mme, gmlc) get a Multus secondary
       interface on the signalling VLAN, with hostNetwork off;
     - the UPF gets SR-IOV virtual functions plus hugepages, and runs as
       a DaemonSet on dedicated nodes;
     - everything else uses ordinary ClusterIP services.

   Do not put N2 behind a kube-proxy Service. NGAP association state does
   not survive load balancing.

 8.2 CLUSTER LAYOUT AND SIZING

   Staging, one node, for function only:

     1 x 16 vCPU, 64 GB RAM, 1 TB NVMe, 2 x 10 GbE

   Pre-production, three nodes:

     control plane   3 x 4 vCPU / 8 GB  (k3s or kubeadm)
     signalling      2 x 16 vCPU / 64 GB, SCTP, 10 GbE
                     runs amf, smf, pcf, udm, hss, gmlc, dra, stp
     user plane      1 x 32 vCPU / 64 GB, 25 GbE, SR-IOV,
                     16 GB hugepages, NUMA aligned
                     runs upf only

   Separate the user plane. A noisy data plane evicting the AMF is a
   signalling outage caused by a download.

 8.3 MULTUS AND SR-IOV

     Multus with a macvlan NetworkAttachmentDefinition per VLAN is
     enough for staging and for Diameter. SR-IOV is for the UPF only.

     Staging definition:
       apiVersion: k8s.cni.cncf.io/v1
       kind: NetworkAttachmentDefinition
       metadata: { name: signalling }
       spec:
         config: |
           { "cniVersion": "0.3.1", "type": "macvlan",
             "master": "eth1", "mode": "bridge",
             "ipam": { "type": "whereabouts",
                       "range": "10.1.13.0/24" } }

     Annotate the pod with k8s.v1.cni.cncf.io/networks: signalling and
     give it the address from section 4.2.

   Install Multus, the SR-IOV device plugin and operator before any NF
   pod. Retrofitting them after a working cluster is a rebuild.

 8.4 WORKLOADS

     Deployment       amf, smf, pcf, udm, ausf, chf, nrf, hss, gmlc, dra
     StatefulSet      mariadb, mongo, redis if self-hosted
     DaemonSet        upf, node exporter, packet capture agent
     Job / CronJob    DB migrations, CDR rollup, route table sync

   Every NF gets a readiness probe that proves its dependency, not just
   that its port is open: the AMF readiness should fail if it cannot
   reach the NRF. A readiness probe that is a TCP connect is a lie.

 8.5 STORAGE

   Subscriber and CDR data must survive a node loss and fsync. Use a
   storage class that does not lie about durability. Local-path is fine
   for staging and wrong for pre-production. For three nodes, Longhorn
   or a replicated MariaDB plus object storage for CDRs is the cheaper
   correct answer.

 8.6 NETWORK POLICY

   Default deny between namespaces. Explicit allow:

     amf  -> nrf, udm, ausf, pcf, lmf
     smf  -> nrf, upf, udm, pcf, chf
     gmlc -> dra, hss/udm, lmf
     dra  -> every served peer, nothing else
     hss  -> db only

   The DRA policy is the interesting one. If the DRA can reach the
   database, it will eventually be given a reason to read it.

 8.7 OBSERVABILITY

     prometheus + grafana for NF metrics
     a capture agent on the signalling VLAN, feeding CNA if licensed
     node exporter and sctp metrics
     alert on: association down, Diameter error rate, PFCP session
     drop, CDR write failure, readiness flapping

 8.8 MIGRATION PATH

     1  compose profiles correct and tests green (sections 3 and 5)
     2  single-node k3s, same images, Multus, one NF moved: the DRA
     3  DRA traffic stable for a week, then move the GMLC
     4  AMF and SMF, then UPF on the user-plane node
     5  freeze compose; it becomes the development environment only

   Move one NF at a time and keep the ability to fall back for one
   release. Big-bang migrations to Kubernetes are how pilots die.

 8.9 WHAT NOT TO DO

     - do not run the UPF in a pod without SR-IOV or DPDK;
     - do not share a node between the UPF and the AMF;
     - do not use NodePort for Diameter or NGAP;
     - do not store CDRs only in a container filesystem;
     - do not let the DRA or the STP hold subscriber state.


9. TERRAFORM AND THE LINUX BASELINE

 9.1 WHERE TERRAFORM FITS

   Terraform provisions hosts and networks. It does not configure the
   core. Keep the boundary sharp:

     terraform   VLANs, subnets, VMs or bare-metal allocation, DNS,
                 firewall, load balancers, object storage for CDRs
     ansible     OS baseline, kernel, sysctl, hugepages, packages
     gitops      Kubernetes manifests and NF configuration

 9.2 PROVIDER CHOICE

     staging on a workstation or an on-prem box
       libvirt or bpg/proxmox provider, cloud-init, one module per host
     colo
       whatever the facility offers; if it is bare metal, use a small
       Terraform that only allocates and a full Ansible that configures
     cloud
       only for the signalling-light parts; the UPF wants a real NIC

 9.3 MODULE LAYOUT

     terraform/
       modules/network      VLANs, subnets, routes
       modules/host         VM or bare metal, disks, NICs
       modules/k8s          k3s or kubeadm bootstrap
       modules/dns          realm and NF records
       envs/staging         one node
       envs/preprod         three nodes

   Remote state with locking from the first commit. A state file on a
   laptop is how two people build two different networks.

   Terraform variables are not secrets. Put credentials in SOPS or in a
   secret manager and reference them. The .env.example defaults must
   never reach a pre-production host.

 9.5 THE LINUX BASELINE (ANSIBLE)

     OS            Ubuntu 22.04 LTS or Debian 12
     kernel        5.15 or newer, for gtp5g and modern SCTP
     packages      lksctp-tools, tcpdump, chrony, iperf3, tuned
     time          chrony against at least two sources; every CDR and
                   every authentication depends on it
     tuned         throughput profile on the UPF node

 9.6 SYSCTL AND KERNEL, EXPLICITLY

     net.ipv4.ip_forward = 1
     net.ipv6.conf.all.forwarding = 1
     net.core.rmem_max = 33554432
     net.core.wmem_max = 33554432
     net.core.netdev_max_backlog = 250000
     net.sctp.rmem_max = 33554432
     net.sctp.wmem_max = 33554432
     net.sctp.association_max_retrans = 10
     net.sctp.path_max_retrans = 5

   SCTP parameters are not defaults you can leave. An interconnect that

 9.7 HOST FIREWALL

   nftables, default drop, allow:

     22/tcp        from the management network only
     Diameter      from configured peer addresses only
     M3UA          from the MTN interconnect addresses only
     GTP-U         from the RAN and the peer UPF only
     NGAP          from the gNB addresses only

   Everything else closed. In a telecom core the firewall is not a
   hygiene measure; it is part of the product.

 9.8 THE BUILD SEQUENCE

     1  terraform apply, staging
     2  ansible baseline, reboot, verify sysctl and SCTP
     3  k3s, Multus, whereabouts, MetalLB
     4  namespaces and network policies
     5  databases, migrations
     6  NRF, then the NFs in dependency order
     7  DRA and STP, with the firewall rules from section 7
     8  run section 5 from a test runner in the cluster

   Each step has a check. A step without a check is a hope.


10. STAGING TO PRE-PRODUCTION GATE

   Both must be true to promote a build:

   TECHNICAL
     - every test in section 5.15 passes on a clean deployment
     - every P0 in section 3 is closed and has a regression test
     - no service depends on a mock in the promoted profile
     - a restart of any single NF loses no CDR and no session record
     - the firewall rejects TFW.1 to TFW.10

   OPERATIONAL
     - one command deploys from clean; one command rolls back
     - config is in git; secrets are not
     - dashboards exist for the eight alerts in 8.7
     - a named person owns each NF and its runbook

   If either list has a gap, the correct action is to name the gap, not
   to schedule around it.

14.1 SUCI DE-CONCEALMENT (TS 33.501 ANNEX C)

   New file: udm/src/suci.py. Wired into udm_server.py through
   resolve_identity() and deconceal_suci().

   Scheme 0 (null)      MSIN returned as decimal digits.
   Scheme 1 (Profile A) ECIES over X25519.
   Scheme 2 (Profile B) ECIES over secp256r1 (SEC1 compressed or
                        uncompressed point accepted).

   Construction, identical for both profiles:
     Z          = ECDH(home network private key, UE ephemeral public key)
     K          = ANSI X9.63 KDF (SHA-256, counter 1..n, SharedInfo = the
                  UE public key as transmitted; Profile B always uses the
                  compressed form)
     enc_key    = K[0:16], ICB = K[16:32], mac_key = K[32:64]
     MAC        = HMAC-SHA-256(ciphertext, mac_key)[0:8]
     plaintext  = AES-128-CTR(enc_key, ICB, ciphertext)
     MSIN       = nibble-swapped BCD, trailing 0xF removed

   Scheme output layout: PK_UE || ciphertext || MAC(8), where PK_UE is
   32 octets for Profile A and 33 or 65 octets for Profile B.

   Key custody:
     SUCI_PROFILES                JSON array, highest precedence
     SUCI_PROFILE_A_PRIVATE_KEY   32 hex octets
     SUCI_PROFILE_A_PKID          key id used in the SUCI (default 1)
     SUCI_PROFILE_B_PRIVATE_KEY   same for Profile B
     SUCI_PROFILE_B_PKID          default 2

   Keys are read from the environment, never from the repository, and
   /health exposes only pkid, scheme and the derived public key.

   Failure causes, each with its own HTTP status and cause string:
     SUCI_MALFORMED                 400  bad syntax or non-hex output
     SUCI_UNSUPPORTED               400  NAI SUCI, or pkid and scheme mismatch
     SUCI_AUTHENTICATION_FAILED     400  MAC mismatch, bad point, unknown pkid
     SUCI_KEY_NOT_CONFIGURED        500  no key provisioned; never guesses

   The UDM image now installs cryptography==41.0.7. pycryptodome remains
   for Milenage; the two libraries serve different purposes.

   tests/test_suci.py (13 tests) covers A and B round trips, MAC
   tampering, wrong key, unknown pkid, scheme mismatch, null scheme,
   malformed input, environment loading and the health summary.

14.2 CORE LIBRARY (corelib/)

   corelib/diameter.py      RFC 6733 header and AVP codec with correct
                            V (0x80) and M (0x40) bits, 4-octet padding,
                            grouped AVPs, an asyncio TCP server, and
                            answer() that always names this node as
                            Origin-Host instead of echoing the peer.
                            Constants for SLg (16777255, 8388620), SLh
                            (16777291, 8388622), S6a, Gx and Gy.
   corelib/nrf_client.py    TS 29.510 register, heartbeat, deregister and
                            discovery on a daemon thread with backoff.
                            Failures never stop the NF; they surface in
                            /health.
   corelib/http.py          JSON over urllib, so the new nodes need no
                            third-party HTTP client.

   diameter/src/diameter_server.py predates corelib and still has its own
   codec, in which the V and M bits are swapped. The new nodes do not use
   it. Migrating S6a to corelib is the next cleanup item.

14.3 CUSTOM AMF (amf/, host port 8001)

   Registers with the NRF as NF type AMF (services namf-loc, namf-comm)
   and forwards:

     POST /namf-loc/v1/{supi}/provide-loc-info
       discovers an LMF through the NRF (cached 10 s), posts to
       /nlmf-loc/v1/determine-location and relays the result.
       503 LMF_NOT_REGISTERED when discovery finds nothing,
       504 LMF_UNREACHABLE when the endpoint does not answer.

     POST /namf-loc/v1/{supi}/event-notify      501
     POST /namf-loc/v1/{supi}/cancel-pos-info   501
     POST /namf-comm/v1/ue-contexts/...         501
       Deferred location and NAS transfer need NGAP and NAS, which are
       not built. The causes say so.

     GET /n2/status     listening=false, reason NGAP not implemented
     GET /health        n2_ngap not implemented, ue_attach false

   This AMF cannot attach a UE. It is the service-based hop between the
   location layer and the SBI, and it is honest about the gap.

14.4 CUSTOM LMF (lmf/, host port 8003)

   Registers as NF type LMF (service nlmf-loc).

     POST /nlmf-loc/v1/determine-location
       With LMF_PROVIDER_URL empty: 501 NO_POSITIONING_SOURCE.
       With a provider: forwards the request, checks that latitude and
       longitude are numbers inside their ranges, and returns a POINT
       geographicArea. Provider failures map to 504 PROVIDER_UNREACHABLE,
       502 PROVIDER_ERROR or 502 PROVIDER_INVALID_RESPONSE.

     POST /nlmf-loc/v1/location-context-transfer      501
     POST /nlmf-loc/v1/upiuci/{supi}/cancel-location  501

   The LMF never generates a position. A provider that returns simulated
   coordinates is an operator decision and is visible in the response's
   provider field.

14.5 MME (mme/, Diameter 3875/tcp, HTTP 8075)

   One process, two listeners in the same asyncio loop:

     Diameter SLg    CER/CEA and DWR/DWA answered with success.
                     PLR -> PLA with Result-Code 5012
                     DIAMETER_UNABLE_TO_COMPLY and an Error-Message naming
                     the missing S1-MME association.
                     PLR for a foreign Destination-Realm -> 3003.
                     Unknown command -> 3001.
     HTTP            /health, /slg/status, /scope and /slg/plr (a JSON shim
                     that runs the same decision path for tests).

   Not built: S1AP, S11, S6a, SGs, paging, bearers. A UE cannot attach to
   this MME. It exists so that a GMLC or an external MME peer gets a
   protocol-correct failure instead of a hang.

   MSC: deliberately not built. An MSC needs MAP LCS (SLR/SLA, opcodes
   85/86) over SCCP plus call control. A stub that answers MAP without a
   visitor location register would be worse than nothing. The DRA/STP
   layer already carries the SS7 transport for when that work starts.
